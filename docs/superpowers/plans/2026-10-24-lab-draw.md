# The Lab Draw — Implementation Plan

**Spec:** `docs/superpowers/specs/2026-10-24-lab-draw-session-prompt.md`. Where this plan and the spec disagree, the decisions below win. They were confirmed with Lewis on 2026-10-24.
**Prototype:** `docs/prototypes/the-lab-draw.html`. Match its flow, copy structure and card treatment.
**Branch:** `feat/lab-draw`. One commit per task or more. Never push.

## Confirmed decisions (override the spec where they differ)

1. **Admin lockdown first.** Today every signed-in Supabase user is effectively an admin: the middleware, the admin layout and the admin APIs check only that a user exists, and RLS uses `auth.role() = 'authenticated'`. Magic links would make that public. The fix is an `admin_users` table plus a SQL `is_admin()` function, used in every admin RLS policy and in app code.
2. **SQL location.** Numbered files in `supabase/migrations/`: `015_admin_lockdown.sql` and `016_lab_profiles.sql`. They are raw SQL that Lewis runs by hand in the dashboard. Never run SQL against Supabase from a tool: no MCP `apply_migration`/`execute_sql`, no `supabase db push`.
3. **Visual system.** Use the site's sunset palette tokens from `tailwind.config.ts` (`cream2`, `deepBrown`, `midBrown`, `warmRust`, `gold2`, `goldLight`, `forest`, `cardCream`, `cardBorder`, `coral2`, etc.) and the site's loaded fonts (Fraunces, Cormorant Garamond, Spectral, Outfit, Syne, DM Mono, Caveat via `--font-*` vars). Do not add Playfair or Poppins. Card treatment: card back in `forest`, with a `gold2` border, an inner hairline and the original SVG sun motif; card face in `cardCream`.
4. **Events.**
   - *Pre-email* steps (`lab_card_drawn`, `lab_birth_submitted`, `lab_result_viewed`) go through the existing client `track("interaction", "<name>", { src, card, has_time })` from `lib/analytics/track.ts`, which writes to `analytics_events`. No schema change is needed.
   - *Post-email* steps (`lab_email_submitted`, `lab_profile_opened`, `lab_booking_clicked`) are written server-side with the service-role client to `lead_events`, with `lead_id` pointing at a `leads` row (`source = 'lab'`), `type = <event name>`, `source = 'website'` and `detail = { src, card, has_time }`.
5. **Meta Pixel.** A consent gate exists (`context/ConsentContext.tsx`, `components/MetaPixel.tsx`). On a successful gate submit, fire `trackLead(email)` from `lib/fbpixel.ts`, but only when `useConsent().marketingAllowed` is true.
6. **Route placement.** The Lab pages sit inside the `(public)` route group (`app/(public)/lab/page.tsx` and `app/(public)/lab/profile/page.tsx`) so they get the site header and footer. The homepage is `app/(public)/page.tsx`. The existing `components/TarotDeck.tsx` is the paid service deck and must not change. The Lab deck component is `components/lab/LabDeck.tsx`.
7. **English only** for all `/lab` copy.

## Global Constraints

- **Never run SQL against Supabase** (production or otherwise) via any tool. Write SQL files only.
- **Do not modify** `components/TarotDeck.tsx`, `components/booking/*`, `lib/booking.ts`, `lib/payments/*`, or the service cards' booking links. The only homepage change allowed is adding a teaser section below the service cards.
- **No GPL or AGPL dependencies.** No `swisseph`, `pyswisseph` or `kerykeion`. Verify each new dependency's licence from its `package.json` in `node_modules` and record it in the task report.
- **Interpretive copy lives only in `content/lab/*.ts`**, never inline in components. Each content file starts with `// DRAFT — Gabs to rewrite in her voice`.
- **Stance:** "the chart is a prompt, not a cause". No causal or predictive language (not "Saturn will make you…").
- **Never log birth data** (date, time, place, coordinates, positions) or emails to the console. Log error messages and codes only.
- **Unknown birth time** means no rising sign and no houses anywhere. A position whose sign changes across the birth day (local 00:00 to 23:59) is shown as "X or Y". Never guess.
- **Tests** use Vitest. The config includes `**/*.test.ts`, so name test files `*.test.ts` (in `__tests__/` folders or alongside the code). Run them with `npx vitest run <path>`. `npm run lint` and `npx tsc --noEmit` must pass.
- **Server-only secrets** (`SUPABASE_SERVICE_ROLE_KEY`, `MAILERLITE_API_KEY`, `CRON_SECRET`) are never imported into client components. The service-role client is `createAdminClient()` from `lib/supabase/admin.ts`.
- **Commit messages** use conventional style (`feat(lab): …`, `fix(admin): …`) and end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- **Match the surrounding code style:** comment density, naming, and defensive fetch handling like `lib/mailerlite.ts`.
- **New env vars:**
  - `MAILERLITE_LAB_GROUP_ID`
  - `NOMINATIM_USER_AGENT`, e.g. `AstropsycheLab/1.0 (contact@...)`
  - `NEXT_PUBLIC_SITE_URL`
  - `CRON_SECRET`
  - `SUPABASE_SERVICE_ROLE_KEY` already exists in code

  Each one must degrade with a clear server error message when it is missing, never crash the page.

## Task 1: Astro engine (`lib/astro/`)

**Dependencies.** Install `astronomy-engine`, `luxon`, `@types/luxon` (dev) and `tz-lookup`. Verify the licences in `node_modules/*/package.json`: astronomy-engine should be MIT, luxon MIT, tz-lookup CC0-1.0. If `tz-lookup` lacks types, add a minimal `types/tz-lookup.d.ts`. Report the installed versions.

**Files**
- **`lib/astro/types.ts`:**
  - `Body = "Sun"|"Moon"|"Mercury"|"Venus"|"Mars"|"Jupiter"|"Saturn"|"Uranus"|"Neptune"|"Pluto"|"NorthNode"`
  - `Sign` (the 12 English names)
  - `Position = { body, lon, sign, degree, retrograde? }`
  - `ChartPoint = Body | "Ascendant" | "MC"`
- **`lib/astro/positions.ts`:**
  - `positionsAt(date: Date): Record<Body, number>` returns geocentric apparent ecliptic longitude in degrees (0–360) for each body.
    - Use `Astronomy.GeoVector(body, date, true)` plus `Astronomy.Ecliptic(vec).elon`.
    - The Moon can use `Astronomy.EclipticGeoMoon`, and the Sun `Astronomy.SunPosition(date).elon`. Use whichever is accurate, of date.
    - The mean lunar node uses Meeus's formula: Ω = 125.04452 − 1934.136261·T + 0.0020708·T² + T³/450000, with T in Julian centuries TT from J2000.
  - `isRetrograde(body, date)` compares longitude at ±12h.
- **`lib/astro/signs.ts`:**
  - `SIGNS` in zodiac order
  - `signOf(lon)` and `degreeInSign(lon)`
  - `signsOverWindow(fn: (d: Date) => number, start: Date, end: Date, stepMinutes = 60): Sign[]` returns distinct signs in order and always includes the endpoint.
- **`lib/astro/time.ts`:**
  - `zoneFor(lat, lon): string` wraps tz-lookup.
  - `localToUtc(dateISO: "YYYY-MM-DD", timeHHMM: string | null, zone: string): { utc: Date; dayStartUtc: Date; dayEndUtc: Date; approximateZone: boolean }`.
    - Use Luxon `DateTime.fromISO(..., { zone })` with historical rules.
    - With no time, `utc` is local noon.
    - `dayStart` is local 00:00 and `dayEnd` is local 23:59.
    - `approximateZone` is true when the year is before 1970.
  - Throw a typed error on an invalid zone or date.
- **`lib/astro/houses.ts`:**
  - `computeHouses(utc: Date, lat: number, lon: number): { system: "Placidus" | "WholeSign"; ascendant: number; mc: number; cusps: number[] /*12*/ }`.
  - Use local sidereal time from `Astronomy.SiderealTime(date)` (GAST in hours) plus east longitude, and true obliquity (`Astronomy.e_tilt(Astronomy.MakeTime(date)).tobl`, or the mean obliquity formula).
  - ASC = atan2(−cos RAMC, sin RAMC·cos ε + tan φ·sin ε), adjusted into the correct quadrant. MC = atan2(sin RAMC, cos RAMC·cos ε).
  - Use Placidus (iterative semi-arc method for cusps 11, 12, 2 and 3, with opposite cusps +180°) when |lat| ≤ 66. Above that, use Whole Sign: cusp 1 is 0° of the ASC sign, then +30° each. Never throw.
  - `houseOf(lon, cusps): number` returns 1–12.
- **`lib/astro/aspects.ts`:**
  - `ASPECTS = { conjunction: 0, sextile: 60, square: 90, trine: 120, opposition: 180 }`
  - `findAspect(a, b, orbs = { default: 6 }): { type, orb } | null`, with a configurable orb per aspect
  - `angularDistance(a, b)` returns 0–180
- **`lib/astro/chart.ts`:**
  - `computeChart({ dateISO, timeHHMM | null, lat, lon, zone })` returns `{ birthUtc, hasTime, approximateZone, positions: Position[], ambiguous: Partial<Record<Body, Sign[]>>, houses: (computeHouses result) | null, rising: Sign | null }`.
  - Ambiguity is computed only when `timeHHMM` is null, over dayStart to dayEnd for every body, and it lists only the bodies whose sign actually changes.
  - With no time, `houses` and `rising` are null and positions carry no house.
  - With a time, each position gets a `house`.
- **`lib/astro/index.ts`:** re-exports.

**Tests** (`lib/astro/__tests__/*.test.ts`)
- **2024-04-08 eclipse at 18:21 UTC:** Sun and Moon each between 19.0° and 19.5° Aries (lon 19–19.5), and within 0.1° of each other. Widen to 0.2° only if the true apparent values differ that much. The reference is about 19.2° and about 0.05° apart.
- **2000-01-06 at 18:14 UTC:** Sun and Moon both within 0.3° of 285.8°.
- **Gabs fixture:** read `lib/astro/__tests__/fixtures.local.json` if it exists (`{ dateISO, timeHHMM, lat, lon }`) and skip with `it.skipIf(!exists)` otherwise. Expect a Pisces Sun, a Sagittarius Moon and Taurus rising. Add `lib/astro/__tests__/fixtures.local.json` to `.gitignore`. Also commit a `fixtures.example.json` showing the shape, with dummy values.
- **Ambiguity:** pick a date when the Moon changes sign mid-day. Find one by computing it in the test setup, scanning a month for a day where `signsOverWindow` gives two Moon signs over 00:00–23:59 UTC, then assert that `computeChart` with `timeHHMM: null` and zone `"UTC"` returns two Moon signs.
- **High latitude:** Tromsø (69.65, 18.96) returns `system: "WholeSign"` without throwing. London (51.5, −0.13) returns Placidus.
- **ASC sanity:** for 2000-01-01 12:00 UTC at lat 0, lon 0, the ASC is within 1° of a reference value derived independently in the test from the closed-form formula. Better: assert that ASC − MC is in the expected quadrant and that MC is within 1° of the RAMC-derived value.
- **Time:** `localToUtc("1985-07-01","14:30","Europe/London")` gives 13:30Z (BST). A 1960 date gives `approximateZone: true`.

## Task 4: API routes and auth callback

- **`app/api/lab/compute/route.ts` (POST)** takes `{ date, place, time?, card, src? }`.
  1. Rate-limit by IP and return 429 with a friendly message when over the limit.
  2. Validate the input and return 400 `{ field, error }` on failure.
  3. Geocode (null gives 404 `{ field: "place", error: "We couldn't find that place. Try city and country." }`; busy gives 503 with a retry message).
  4. `computeChart`, then `composeReading`.
  5. Return `{ reading, chart: { hasTime, approximateZone, positions, ambiguous, rising }, place: { displayName, lat, lon, tz }, attribution: "© OpenStreetMap contributors" }`.

  `export const dynamic = "force-dynamic"`. Never log the body.
- **`app/api/lab/gate/route.ts` (POST)** takes `{ email, time?, consent: true, consentVersion, card, date, place, src? }`.
  - Re-validate and re-geocode (the cache makes this cheap) and recompute server-side. Never trust client positions. If `consent !== true` or the version does not match `CONSENT_TEXT_VERSION`, return 400.
  - Upsert `lab_profiles` by email where `deleted_at` is null: update if found, otherwise insert, through the admin client. Set `consent_at` to now.
  - Call `supabase.auth.signInWithOtp({ email, options: { emailRedirectTo: \`${NEXT_PUBLIC_SITE_URL}/auth/callback?next=/lab/profile\`, shouldCreateUser: true } })` using the cookie-based server client from `lib/supabase/server.ts`.
  - `upsertLabSubscriber` (awaited with its timeout; failure does not fail the request).
  - `recordLeadEvent(type: "lab_email_submitted")` and store the returned `lead_id` on the profile.
  - Return `{ ok: true }`. On an OTP error, return 502 `{ error: "We couldn't send the sign-in link. Try again in a minute." }`.
- **`app/auth/callback/route.ts` (GET):** `exchangeCodeForSession(code)`. Then, with the admin client, set `lab_profiles.user_id = user.id` where `lower(email) = lower(user.email)`, `user_id is null` and `deleted_at is null`. Redirect to `next` only when it is a relative path starting with `/` and not `//`, otherwise to `/lab/profile`. On error, redirect to `/lab?auth=error`.
- **`app/api/lab/delete/route.ts` (POST, authenticated user):** look up the user's profile. Set `deleted_at = now()`, null out the birth fields that are nullable, and replace `positions` with `'{}'`. The NOT NULL columns keep their values; the soft-delete flag hides them. Ruling: keep the schema simple; the cron and views ignore deleted rows. Then `forgetSubscriber(email)`, sign the user out, and return `{ ok: true, mailerlite: boolean }`.
- **`app/api/lab/event/route.ts` (POST, authenticated user):** accepts only `{ type: "lab_booking_clicked" }` and records it via `recordLeadEvent` with `detail` built from the user's profile (`src`, card, `has_time`). It returns 204.
- **`app/api/lab/birth-time/route.ts` (POST, authenticated user):** `{ time }`. Recompute the chart from the stored date, coordinates and zone with the new time, then update `birth_time`, `birth_utc` and `positions`. Return `{ ok: true }`.
- Tests are optional for the routes. If they are written, mock the libraries; the libraries are already unit-tested in Task 3.
- **`positions` jsonb shape** (shared with Tasks 5–7): `{ version: 1, hasTime, approximateZone, positions: Position[] (with house when hasTime), ambiguous, houses: { system, ascendant, mc, cusps } | null, rising }`. Export the type as `StoredChart` from `lib/lab/types.ts`.

## Task 7: Transit tracker and monthly cron

- **`lib/astro/transits.ts`:**
  - `findTransits({ natal: Record<"Sun"|"Moon"|"Rising"|"Venus"|"Saturn", number | null>, from: Date, to: Date, planets = ["Jupiter","Saturn","Uranus","Neptune","Pluto"], aspects = ["conjunction","square","opposition","trine"], orb = 1 })` returns `TransitSeason[]`.
  - Scan daily. For each planet × aspect × target angle (the aspect angle, which gives two targets for square and trine: +angle and −angle), find the days where the signed separation crosses zero, and refine to the hour by bisection. Those are the exact hits.
  - Group hits of the same planet, aspect and point that fall within 300 days of each other (retrograde passes) into one season: `{ planet, aspect, point, exactDates: Date[], start: Date, end: Date, peak: Date }`.
    - `start` and `end` are when the separation is within the 1° orb.
    - `peak` is the first exact date that is on or after `from`, or the last exact date if none is.
  - Also include seasons that are within the orb at `from` even if their exact hit fell before it.
  - Sort by `peak`.
  - Skip null natal points (Rising without a time).
  - "Significant" ordering: the next season by peak date, with ties broken by planet weight (Pluto > Neptune > Uranus > Saturn > Jupiter).
- **Tests:**
  - a synthetic check: a natal Sun placed at Saturn's longitude on a known date gives a conjunction season containing that date
  - a retrograde case: Jupiter around a station (find one by scanning for a sign change in daily motion, in the test setup) gives one season with 3 exact dates when a natal point sits at the station's longitude ±0.5°
  - Rising null is skipped
- **`components/lab/TransitTracker.tsx`:** the profile page computes `findTransits` server-side for the next 12 months from the stored chart. The component shows the next season prominently (headline from `transitCopy`, peak date formatted in `en-GB` long form, every exact date listed when there are several, then the astro, psych and test layers in a `LabNote`), followed by a list of the following four (headline plus peak date). Wire it into the profile page.
- **`app/api/cron/lab-transits/route.ts` (GET):**
  - Require `Authorization: Bearer ${CRON_SECRET}` (this is what Vercel Cron sends). Return 401 otherwise, and 500 if the env var is missing.
  - For each profile where `deleted_at` is null (paged, 200 at a time), compute the next season and update `next_transit` (the headline) and `transit_peak_date`. Then `updateLabFields(email, { next_transit, transit_peak_date })`, sequentially with small delays to respect MailerLite's 120 requests per minute.
  - Return `{ processed, updated, mailerliteFailures }`.
  - `export const maxDuration = 300` where supported.
- **`vercel.json`:** create it, or merge if it exists. Add `{ "crons": [{ "path": "/api/cron/lab-transits", "schedule": "0 6 1 * *" }] }`.
- The gate route (Task 4) should also set `next_transit` and `transit_peak_date` at creation and include them in `upsertLabSubscriber`. Update it.
